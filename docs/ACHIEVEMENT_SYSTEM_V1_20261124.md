# 「向前」成就系统｜开发路线与内容规格 V1.0

> 状态：**产品规格定稿，尚未开始修改代码**  
> 适用：Android App「向前」  
> 日期：2026-11-24  
> 优先级：现有功能和数据安全 > 解锁判定正确 > 内容完整 > 界面与动效 > 扩展玩法

## 0. 产品决策（本轮冻结）

1. **成就图鉴总规划 108 个解锁里程碑**：8条进化成长线×6阶段＝48；5组独立行为×6＝30；3组挑战×6＝18；隐藏成就12。108 是内容规划，不等于当前必须同时开放108张卡片。
2. **保留上一轮已确认的命名方向**：现代自然中文，有趣、有余味、有纪念感；不生造古风四字词，不照搬任务描述，不用浮夸游戏黑话。第16系列和12枚隐藏成就采用本文件修订版本。
3. **高难度必须来自真实成本和可靠证据**。不只靠累计数字，不为稀有而人为诱导熬夜、放弃休息、过度专注或完全不娱乐。
4. **进化系列的每个阶段是可记录的独立里程碑，但图鉴默认折叠为1个系列收藏位**；历史阶段在详情中回看，图鉴不摊开48张重复形态。独立、挑战、隐藏各为独立收藏位。
5. **成就第一阶段不发放可兑换娱乐额度/游戏局数**，避免与现有任务奖励与娱乐账本叠加造漏洞。V1仅提供徽章、解锁记录和收藏；以后如加入成就XP，必须使用一次性幂等奖励流水和可冲回规则，且不直接兑换娱乐额度。
6. **不擅自改变现有行为约束系统**：逐项必做即时奖励、统一娱乐时长池、游戏局数、睡眠惩罚、严格紧急解锁、每日额度上限、任务跨日和奖励4:00重置均属于原模块，不因成就开发而改语义。
7. **成就系统采用“正式事件核验→状态计算→图鉴呈现”**，不得使用 UI 页面运行次数、打卡按钮点击次数或重复推送次数判定解锁。
8. **先建可靠内核，再扩图鉴和制作美术。** 不在源码未知时假设使用Room、Compose或某个数据库；先以项目真实架构为准。

## 2. 成就内容结构（每个条目必须具备）

配置文件每枚成就必须至少包含：

- `id`：稳定唯一、不可用名称做主键（例如 `achievement.breakthrough.not_luck`）；
- `seriesId`、`stage`（进化线）、`kind`：evolution / independent / challenge / secret；
- `title`：现代、自然、有记忆点的正式名称；
- `description`：不超过40个汉字、用自然语言描述意义，不写空泛鸡汤；
- `unlockRule`：机器可判定的数据来源、计量单位、时间窗口、去重规则、阈值；
- `rarity`：普通/进阶/困难/史诗/传说；区分**稀有度**与**是否隐藏**；
- `releaseStatus`：draft / pending_evidence / available / retired；绝不把未支持条件包装为可领取；
- `artId`、`artVariant`、`unlockedIllustration`：图案资产及已解锁效果；
- `evidencePolicy`：自动核验、人工审核、当前不可验证；
- `version`：规则版本，保证迁移兼容；
- `unlockedAt`、`evidenceRefs`、`sourceVersion`：用户实际解锁元数据保存在状态/流水表，不写在静态配置中。

**每个条目做内容审核时，必须同时通过**：名称不生造；条件不重复；难度有分层；行为有实际价值；证据可验证；有独立视觉主题；不诱导不健康行为。

## 3. 难度体系与防刷原则

- 不靠“所有成就都难”营造稀有感。首次类成就保留少量（约10%）；主要目标在30天、90天、1年和数年。
- 难度标注以**实际所需努力和难以伪造程度**为主，不只看阈值。连续365个有效日与6000次有效任务并非相同维度，不能简单比较数字。
- 每个任务实例在指定统计周期内最多贡献一次有效完成；撤销完成、删除/修正记录需要重算。不能因午夜自动重复生成任务而重复记账。
- 高质量全清日依据当天的冻结计划与有效执行记录计算；不可通过临时删除必做项制造“全部完成”。合理改期、请假和暂停保持原系统语义，并可从完成率分母排除，但需有审计记录。
- 专注只按真实有效时长计数，不按用户输入的计划时长。断点、后台运行和屏幕熄灭的计入规则要与现有专注模块一致；无法区分真假的不要擅自称“深度专注”。
- 娱乐只有在可靠使用记录足够时才判断“主动停止”“未超额”“只打一局”；尤其游戏局数自动识别未稳定前，相关成就保持 `pending_evidence`。
- 睡眠类必须区分记录/打卡与实际睡眠证据。手动登记可纳入普通日志，但不能自动证明自然醒或深度达标；必要时设计“已记录”与“已验证”的不同指标。
- 正式暂停豁免日：不增加连续有效执行天数，但不因合法暂停立即破坏连续链；允许的暂停配额直接沿用主系统规则，不另创处罚。缺失记录≠违规，也≠达标。
- 各种百分比条件必须明确分母，缺少有效样本时不得轻易解锁；例如90天窗口的“90%完成率”必须同时有**最低有效日数**（建议≥60天）和冻结任务计划，避免只有1个任务也算100%。
- 内容解锁以徽章收藏为主，不直接叠加娱乐额度，防止成就系统反过来破坏自律约束。

## 4. 数据结构与计算引擎（实现约束）

### 4.1 技术路线

采用**配置驱动的成就目录 + 单一领域事件来源 + 幂等解锁流水 + 可回放进度计算器**，不得再造一个平行的任务、睡眠或娱乐账本。

最低必要结构：

- `AchievementDefinition`：静态成就内容、规则参数、发布状态、资产映射和版本。
- `AchievementProgress`：当前统计窗口、进度、计算版本、最近更新时间（可由现有业务表派生）。
- `AchievementUnlock`：唯一 `achievement_id + account/device_profile` 解锁事件、时间、证据引用、状态及版本；同一成就仅解锁一次。
- `AchievementReconcileLog`：数据修正、恢复/迁移、重算、异常冲突；供开发排查和用户可理解的修正提示。
- `DailyEvidenceSummary`（可选的派生缓存）：任务、专注、娱乐、睡眠等每日快照，严禁成为事实源。

推荐计算流程：

1. 从**已有领域数据**中适配获取 `TaskCompleted/Corrected`、`FocusCompleted`、`AppUsageFinalized`、`SleepCycleFinalized`、`ChallengeVerified`、`PauseConfirmed` 等已提交事件；没有可靠数据源的不伪造。
2. 标准化成统一的日期、身份键、来源、可信等级；事件必须有稳定 `sourceEventId`。
3. 先计算计数/滑动窗口/连续性，再对照 `unlockRule`；晋级时只写一条幂等解锁流水。
4. 应用数据变更、跨日、恢复时重放相关时间窗口；同一结果不重复弹通知或再次发放资产。
5. 对历史可证明的成就允许补发；历史证据不足的高阶成就不猜测解锁。

### 4.2 时间与异常边界

- **任务日以当地自然日00:00切换**；奖励账本原有04:00重置单独存在，成就计算不跟着奖励重置。
- 睡眠跨夜的归属统一锚定**醒来的自然日**，但遵从现有睡眠模块时间戳语义；不能把同一夜算两次。
- 存储UTC时刻及必要的IANA时区信息，日期统计使用原始行为发生地/有效日归属，避免旅行和夏令时引发双算。
- 重复点击完成、同步重复事件、应用崩溃重启、覆盖安装、恢复7份备份中的任一份，都不能重复解锁。
- 补录、撤销、更改任务计划、睡眠纠错、暂停与恢复均有确定性的重新计算策略；对错误解锁可标记 `invalidated` 并保留修正记录，但**对已经合法获得的成就，不因后来调高阈值而追溯撤销**。
- 处理旧版本配置、缺失图案、部分备份、跨版本迁移时默认保留用户既有任务及奖励余额。必须先备份原数据库，再进行受控迁移。

## 5. UI / 视觉 / 动效（与「向前」现有气质一致）

### 5.1 信息架构

仅增加独立的**「成就」**入口和相关解锁反馈，不推翻现有首页结构，不把所有成就卡片平铺到一个页面。建议：

- 成就首页：已解锁收藏数、最近获得、最接近的2–3项（仅公开且有效的成就），下面按“成长／行动／挑战／隐藏”分组。
- 进化系列：8个收藏位，展示最高阶段徽章和进度；进入后是I–VI分级轨迹，允许查看已收藏历史阶段。
- 独立成就：分类网格，支持“已解锁／可追踪／全部”筛选；不在单卡上塞满进度条、条件、标签。
- 详情页：图案为主、名称、简单说明、解锁条件或隐藏状态、当前进度、解锁日期、证据摘要、分享/收藏（分享后续可做）。优先沿用现有底部详情面板的交互习惯。
- 隐藏列表：未解锁只显示统一但有质感的剪影；不能泄漏名称、阈值或进度。已解锁后才展示故事和纪念信息。

### 5.2 美术规格

- 沿用现有**偏灰＋绿**的整体气质：宁静、克制、成熟、精致；可在稀有徽章中少量使用暖金、深蓝、灰紫，但不采用高饱和手游UI。
- 禁止像素风、粗糙金属军衔章、统一圆圈里贴Lucide图标、夸张发光描边、成排廉价彩色卡。
- 主体图形要能联想到对应故事，例如“未完待续”是留有空白页的书，“不是碰巧”是经过重复校准的结构；优先表达场景与意义，而非把名称文字画上去。
- 每条进化系列应有清楚的**同源设计演变**：由外框、结构、细节、材质逐级成长，不许简单换颜色。
- 普通成就：细腻平面与轻材质；史诗：层次更强；传说：独立场景纪念章，不是更大更亮的普通图标。
- 统一1:1画布、可缩放矢量/高分辨率资源、透明背景、安全边距、亮暗色对比。先做1套规范和**12枚高质量样稿**审定，批准后再批量生产；不要一次生成108张风格不一致的AI图片。
- 未解锁、已解锁、获得瞬间的状态要一致。动效短促克制、可关闭或遵守系统减少动画设置；列表滚动与低端机性能必须稳定。

### 5.3 交互

- 解锁反馈可展示专属徽章、名称、达成日期，默认仅一次；多项同时解锁合并通知，不能连续弹十几次。
- 成就进度优先按系列呈现，避免奖励与挑战标签在首页造成认知负担。
- 进化历史可回看，用户能看到自己从I到VI的变化，而不是旧勋章被覆盖消失。
- 手动修正和备份恢复导致状态变化时，使用明确的修正说明，不展示“又获得一次”。

## 6. 分阶段开发路线（不一次性造完）

### P0 · 现状审查与内容基座（先做）

- Agent 阅读项目已有成就页、XP、成就/奖励流水、任务、专注、娱乐、睡眠、备份与数据库结构，列出可复用模块；不得另起一套架构。
- 把108枚内容以独立可校验配置录入；所有无法判断的规则设为 `pending_evidence`，不在用户界面展示为可领取。
- 明确成就ID、进化段位、数据来源及难度，补上静态一致性检查（数量108、ID唯一、系列/阈值单调、无循环依赖、隐藏不泄漏）。

**验收：** 构建与现有功能正常；108枚配置能静态校验；现有数据库和任务/奖励账本未被破坏。

### P1 · 成就计算内核 + 首批真实解锁

- 优先实现4条现成数据最容易核对的进化线：01行动、02全清、03坚持、06选做，共24阶段；以及能用已有事件证明的6枚独立行为成就（从09、13组挑选，不许拿缺失日志来凑数量）。
- 如专注计时有可信会话数据，增加04专注6阶段；如数据源不足，先不开放，保留配置。
- 完成历史记录回填、重放、跨日、暂停、修改记录、备份恢复与单次解锁机制。

**验收：** 对指定历史事件可复现正确结果；恢复不重复通知；改错能确定性修正；进化轨迹可回看。

### P2 · 完整图鉴 UI 和首批精品美术

- 按现有主题做成就主页、进化详情、独立成就目录、隐藏剪影、解锁弹层。
- 完成12枚代表性原创徽章样稿（覆盖进化普通/中/高阶段、独立、隐藏、挑战）；先审美验证再扩量。
- 定向做可用性检查：一眼能分辨已得与未得；详情不拥挤；不会在首页一次摊开108枚。

**验收：** 主要流程可用；字体、色彩、版式和按压响应与「向前」协调；无占位图标冒充最终美术。

### P3 · 娱乐/睡眠/复杂行为扩展

- 接入07娱乐、08睡眠、05深度专注等成长线及10–13组独立成就，先处理数据真实性和时间窗。
- 对天然无法自动核验的“自然醒”“主动停止”“游戏只玩一局”等条目维持不可领取，直到可靠数据源/审核方案完成。
- 扩展经审核的美术素材，按图鉴优先级逐步补齐。

**验收：** 规则与现有娱乐、睡眠和XP账本一致；不鼓励反健康行为；不会因为权限丢失而错误判定违约/解锁。

### P4 · 月度挑战与稀有收藏（最后）

- 挑战系统具备“预先冻结目标—证据—阶段验收—审核—结束”闭环后，才开放14–16组三组共18枚。
- 隐藏成就中依赖挑战、跨领域基线、收藏数量的条目按其依赖解锁开放，不要为凑数量设置假的系统事件。
- 完成传说徽章、专属纪念卡和收藏图鉴的长期扩展。

**验收：** 尤其对16真正的突破，不能凭一次随手完成或改难度获得史诗、传说；隐藏成就条件不会在未解锁视图泄漏。

## 7. 必测场景（定向验收）

1. 完成一项任务→有效累计一次；重复点击/同ID重放→仍然一次。
2. 首次达成多级阈值（例如历史数据回填）→多阶段收藏正确、通知合并。
3. 删除/改期/撤销任务→每日全清、连续天数、滑动窗口正确重算。
4. 午夜00:00任务换日和04:00奖励重置交叠→无错日、双算、奖励改变。
5. 合法 `pause` →不计入有效天数、不直接误判违约；缺记录不自动判违规或达标。
6. 睡眠跨午夜、时区变更、迟录/改录→归属正确、不会同夜双算。
7. 娱乐池余额与真实使用记录不一致/无权限→依规则标记暂不可核验，不作虚假解锁。
8. 游戏局数识别不稳定→“一局就够”不可自动发放。
9. 备份/恢复/覆盖安装/重启→已得成就和历史阶段保留，通知不重复。
10. “重来，不等于重头”：没有正式失败/没有改进/降低标准/不足7天都不得解锁。
11. “不是碰巧”：同一天重复验证不算3次；跨度不足30天不算。
12. “那天，我跨过去了”：无60天过程、无阶段证明、没有年度极限预定级均不得解锁。
13. “一柜子的故事”：进化阶段只计一个系列、不可自己给自己凑到60枚，隐藏/挑战至少6枚。
14. 隐藏列表抓不到真实名称/阈值；解锁后可正常展示记录。
15. 成就触发不新增娱乐可用时长和游戏局数；不破坏任务奖励、睡眠惩罚或紧急解锁约束。
16. Android 真机的深浅色、低性能、无网络、字体缩放、减少动效下界面可用。

## 8. Agent执行规范

- 不重新设计已确定的命名、数量与内容结构；不得擅自开发“社交分享”“排行榜”“AI自动评语”等范围外功能。
- 先读项目现状再定技术方案；能复用现有数据库、事件、奖惩及UI组件就复用。不要把本文件抽象架构误当既定代码结构。
- 按 P0→P1→P2→P3→P4 迭代；每阶段要有可以在真机看到的可用结果，不能停在方案文档或不合并的分支。
- 每次完成修改后运行相关**定向测试**，在具备权限和环境条件时提交、合并main、推送、构建安装并验证实际上运行的版本；遇到权限/环境等真实阻塞才明确汇报。
- 不做无关大重构，不覆盖未提交工作，不清除用户任务/余额/备份。
- 每次报告：本次实现清单、可解锁成就数量、延期项原因、定向测试、提交/推送、真机运行版本及效果。

## 9. 进入开发前仍需由代码审查确认的事实（不是重新问用户）

1. 现有专注模块是否留有真实会话和中断日志。
2. 娱乐时长与游戏局数是否已有足够可信的事件日志，以及权限失效时如何表达缺失。
3. 睡眠记录的来源与可信等级，是否只是手动打卡。
4. 任务计划在当日是否有快照，历史数据能否区分“完成了什么”和“改掉了什么”。
5. 现有成就/XP的唯一ID、数据迁移与备份覆盖范围。

这些信息应由 Agent 阅读仓库并实测获得，不要求用户重复解释。查明后只调整**发布状态与数据适配**，不擅自改写已定的内容与命名。
