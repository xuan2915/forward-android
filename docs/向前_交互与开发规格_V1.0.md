# 向前｜月度挑战交互与开发规格 V1.0

**版本：** 1.0  
**适用平台：** Android  
**技术原则：** 本地优先、模块化、复用现有能力  
**状态：** 开发规格基线  
**开发状态：** 未开始

---

## 1. 技术目标

在不破坏向前现有功能的前提下，增加一套独立的月度挑战模块。

V1.0 必须能够完整运行一个挑战周期：

推荐 → 更换 → 接受 → 执行 → 证据提交 → 验收 → 奖励 → 收藏 → 归档。

不引入新的后端、用户账户或 AI 服务。

## 2. 页面与导航设计

### 2.1 页面结构

采用渐进式信息展示，不将所有功能同时平铺。

#### 页面 A：月度挑战入口

展示：
- 当前月份；
- 推荐挑战或进行中挑战；
- 挑战状态；
- 当前进度；
- 下一项行动；
- 剩余时间。

无挑战时显示挑战书入口及历史收藏入口。

首页只展示一个主挑战卡片，不展示所有挑战模板。

#### 页面 B：挑战书

展示：
- 主视觉；
- 挑战名称；
- 故事开场；
- 核心目标；
- 适用难度；
- 预计时间投入；
- 推荐理由；
- 奖励预览。

底部提供：
- 接受挑战；
- 更换一次；
- 暂时跳过。

更换后必须清晰展示剩余更换机会为 0。

#### 页面 C：接受确认

展示：
- 难度选择；
- 基准测试；
- 时间预算；
- 现实愿望；
- 验收条件；
- 证据要求；
- 好友见证选项。

接受前允许修改配置。

接受后展示冻结的规则摘要。

#### 页面 D：挑战详情

采用单一主行动布局。

顶部：
- 挑战名称；
- 视觉主题；
- 总体进度；
- 剩余天数。

主体：
- 当前阶段；
- 下一项行动；
- 当前里程碑；
- 最近一次进展。

其余内容放在可展开区域：
- 全部里程碑；
- 挑战规则；
- 历史记录；
- 阶段书信；
- 愿望及奖励。

#### 页面 E：证据与验收

支持：
- 图片；
- 文档；
- 文本记录；
- 可选外部链接。

每份证据关联具体里程碑。

最终验收展示：
- 已完成条件；
- 未完成条件；
- 证据；
- 最终结果。

#### 页面 F：结果与收藏

挑战完成后展示：
- 最终回信；
- 实际成果；
- 基准与最终数据对比；
- 获得的 XP；
- 收藏卡；
- 愿望兑现状态；
- 分享入口。

#### 页面 G：成长档案

提供：
- 历史挑战；
- 按类别筛选；
- 已完成与未完成记录；
- 收藏；
- 成长印记；
- 现实愿望兑现记录。

### 2.2 UI 设计约束

1. 不把挑战页面做成普通任务列表。
2. 首页始终只有一个最重要的操作。
3. 使用展开、分层和阶段导航组织内容。
4. 不为展示而添加无关标签。
5. 挑战书、收藏卡和阶段信件保持统一视觉体系。
6. 动画服务于接受、解锁、完成和收藏等重要事件。
7. 不允许动画阻塞关键操作。
8. 页面返回、退出、进程重建后恢复正确状态。

## 3. 推荐引擎

### 3.1 输入

- 当前挑战周期；
- 已完成挑战历史；
- 最近两个月挑战类别；
- 过去六个月模板使用情况；
- 用户设置的时间预算；
- 当前可用挑战模板；
- 用户主动设置的挑战偏好。

### 3.2 筛选

先执行硬性过滤：

- 模板已发布；
- 模板内容完整；
- 时间可行；
- 未被近期重复规则排除；
- 无其他进行中的挑战；
- 所需证据能力可用。

### 3.3 排序

候选优先级考虑：

1. 时间可行性；
2. 历史类别多样性；
3. 最近尚未体验的类别；
4. 用户偏好；
5. 历史挑战完成情况。

不使用黑箱 AI 判断。

### 3.4 推荐结果

推荐引擎只返回：

- 一个主推荐；
- 一个备选（用于唯一一次更换）；
- 推荐理由；
- 不适用原因。

如果候选不足，不允许通过降低硬性条件强行推荐。

## 4. 状态机

### 4.1 状态定义

| 状态 | 含义 |
|---|---|
| OFFERED | 已发放推荐 |
| REPLACED | 已使用更换机会，等待接受 |
| ACTIVE | 挑战进行中 |
| PAUSED | 用户主动暂停 |
| REVIEW_PENDING | 已提交最终验收 |
| COMPLETED | 验收成功 |
| PARTIAL | 部分完成 |
| INCOMPLETE | 未完成 |
| ABANDONED | 主动放弃 |
| SKIPPED | 主动跳过 |
| EXPIRED | 接受窗口过期 |

### 4.2 状态转换

- OFFERED → ACTIVE：接受。
- OFFERED → REPLACED：更换。
- OFFERED → SKIPPED：跳过。
- OFFERED → EXPIRED：超过接受期限。
- REPLACED → ACTIVE：接受替代挑战。
- REPLACED → SKIPPED：跳过。
- ACTIVE → PAUSED：暂停。
- PAUSED → ACTIVE：恢复。
- ACTIVE → REVIEW_PENDING：提交验收。
- REVIEW_PENDING → COMPLETED：通过。
- REVIEW_PENDING → PARTIAL：部分完成。
- REVIEW_PENDING → INCOMPLETE：未达到标准。
- ACTIVE → ABANDONED：主动退出。

任何终态不得自动重新变为进行中。

### 4.3 状态不变量

1. 一个自然月最多创建一个已接受挑战。
2. 同一实例只能接受一次。
3. 每个实例的模板版本和难度快照不可变。
4. 每个里程碑只能完成一次有效结算。
5. 每个挑战只能发放一次完成奖励。
6. 失败和跳过不影响日常任务。
7. 备份恢复不得重新触发奖励发放。

已经接受的挑战不跟随新模板自动更新。

### 5.2 ChallengeInstance

存储用户实际接受的挑战。

字段：

- instance_id
- cycle_id
- template_id
- template_version
- template_snapshot
- difficulty
- status
- recommended_at
- accepted_at
- started_at
- deadline
- timezone_snapshot
- replacement_used
- baseline_data
- wish_data
- reward_snapshot
- final_result
- completed_at

### 5.3 ChallengeMilestone

字段：

- milestone_id
- instance_id
- title
- description
- sequence
- progress_weight
- required
- status
- completed_at
- verification_type

每项挑战的里程碑权重总和必须为 100%。

### 5.4 ChallengeEvidence

- evidence_id

- milestone_id
- evidence_type

- text_content

- created_at

### 5.5 ChallengeEvent

字段：

- event_id
- instance_id
- event_type

- reward_id

- reward_type
- reward_value
- ledger_reference
- grant_status
- granted_at
- idempotency_key

XP 必须复用现有 XP 发放接口。

不得创建第二套 XP 余额。

## 6. 进度与验收引擎

### 6.1 进度计算

根据模板中每个里程碑的权重计算：

进度 = 已完成里程碑权重之和。

只有通过验收的里程碑才计入进度。

证据提交本身不等于里程碑完成。

### 6.2 验收方式

支持三种类型：

**自动验收**

适用于可以从现有数据直接判断的任务，例如完成指定次数的体验记录。

**规则验收**

根据用户提交的数据与预设阈值比较，例如行为执行率。

**人工验收**

适用于作品质量、技能迁移和综合能力等无法完全自动判断的内容。

人工验收必须显示判断依据，不能让系统伪装成具备专业评审能力。

### 6.3 最终结算

只有全部必要条件通过，才允许进入 COMPLETED。

结算采用事务处理：

1. 核对挑战实例。
2. 核对全部必要里程碑。
3. 写入最终验收结果。
4. 写入完成事件。
5. 发放 XP。
6. 解锁收藏。
7. 更新成长档案。

任何一步失败，都不能出现已经发奖但挑战仍未完成，或者挑战完成但重复发奖的状态。

## 7. 与现有系统集成

### 7.1 XP

调用现有 XP 接口。

奖励金额由挑战模板配置。

禁止直接修改用户 XP 总余额。

### 7.2 成就

复用现有成就系统。

挑战完成、类别完成和挑战数量可以作为成就触发事件。

不得重复建立一套互相冲突的成就数据。

### 7.3 娱乐额度

V1.0 不直接发放娱乐分钟和游戏局数。

未来如果增加，必须通过现有奖励账本和每日额度限制。

### 7.4 任务系统

挑战里程碑不自动转换成普通每日必做任务。

如用户希望纳入日常计划，可以提供手动创建关联任务的入口，但不能重复奖励。

### 7.5 睡眠与行为约束

挑战暂停、失败和完成都不能改变睡眠惩罚、紧急解锁及应用管控状态。

### 7.6 备份恢复

挑战数据必须进入现有备份体系。

必须备份：
- 模板版本；
- 挑战实例；
- 状态与事件；
- 里程碑；
- 证据文件或可靠文件引用；
- 奖励结算状态；
- 收藏及成长印记。

恢复时先核对实例 ID 与奖励 ID，再重建展示状态。

不能重新发放历史奖励。

## 8. 本地存储与文件管理

- 挑战模板采用本地结构化配置。
- 用户数据存储在现有数据库体系。
- 证据文件使用应用私有存储。
- 外部文件使用系统文件选择器导入。
- 文件丢失时标记证据不可用，不直接判定挑战失败。
- 删除挑战证据不允许自动删除最终验收记录。
- 分享卡片在本地生成。
- 不需要后端服务。

证据存储应提供合理的文件大小限制和用户可见的存储管理。

## 9. 通知与提醒

V1.0 支持：

1. 月初挑战书通知。
2. 挑战接受期限提醒。
3. 关键里程碑提醒。
4. 最终验收期限提醒。

通知必须允许用户关闭。

不能每天重复发送挑战提醒。

通知权限关闭时，挑战仍可正常使用，相关内容显示在 APP 内部。

## 10. 异常处理

| 异常 | 处理 |
|---|---|
| APP 没有在月初打开 | 首次打开时补展示，未接受不处罚 |
| 推荐数据不足 | 使用保守推荐或允许跳过 |
| 没有可更换挑战 | 不提供无效更换 |
| 证据文件损坏 | 标记缺失，允许重新提交 |
| APP 异常关闭 | 从数据库事件恢复 |
| 任务或奖励重复回调 | 幂等处理 |
| 模板更新 | 已接受实例保持旧快照 |
| 月末仍未完成 | 按实际状态归档 |
| 用户更换设备 | 通过备份恢复 |
| 时区变化 | 已接受实例沿用时间快照 |
| 用户中途卸载 | 仅能通过已有备份恢复，不能承诺未备份数据可找回 |
| 重复完成挑战 | 拒绝重复结算 |
| 奖励发放失败 | 保留待结算状态，恢复后重试 |

### 月末验收宽限期

允许在次月前 48 小时补交证明截止日期前已经完成的行动。

但不能将次月发生的行动算作上月挑战成果。

挑战的实际执行期限不延长。

## 11. 好友与分享

V1.0 通过本地生成图片实现：

- 挑战邀请卡；
- 挑战进度卡；
- 最终成果卡；
- 好友见证卡。

分享内容必须由用户选择。

好友反馈不直接修改验收状态。

不开发账户、好友列表或实时消息。

## 12. 开发实施顺序

### P0：基础架构

- 检查现有数据库。
- 建立挑战数据模型。
- 建立状态机。
- 建立事件与幂等机制。
- 建立本地模板加载机制。
- 接入备份恢复。

### P1：核心流程

- 推荐与更换。
- 挑战书。
- 接受配置。
- 挑战详情。
- 里程碑。
- 证据提交。
- 暂停、恢复、退出。

### P2：结算与收藏

- 最终验收。
- XP 发放。
- 艺术收藏。
- 成长档案。
- 分享卡片。

### P3：体验完善

- 阶段书信。
- 神秘内容。
- 动画。
- 通知。
- 视觉细节。

不得在核心状态、奖励及恢复逻辑不稳定时先做大量装饰动画。

## 13. 开发验收清单

### 产品规则

- [ ] 每月只推荐一个主挑战。
- [ ] 更换机会严格为一次。
- [ ] 更换后不能恢复原挑战。
- [ ] 跳过不产生失败记录。
- [ ] 接受后规则冻结。
- [ ] 每月最多一个已接受挑战。

### 推荐与状态

- [ ] 不重复推荐近期已完成模板。
- [ ] 推荐理由真实。
- [ ] 不符合时间条件的挑战不会出现。
- [ ] 状态转换合法。
- [ ] 已结束挑战不能恢复为进行中。

### 执行与证据

- [ ] 里程碑进度计算正确。
- [ ] 证据能保存及查看。
- [ ] 证据能关联对应里程碑。
- [ ] 允许补交截止日前已产生的证据。
- [ ] 人工验收有明确标准。

### 奖励与成长

- [ ] XP 只发放一次。
- [ ] 收藏只解锁一次。
- [ ] 失败不扣除日常权益。
- [ ] 成就与现有系统正确联动。
- [ ] 不绕过娱乐额度限制。

### 数据与恢复

- [ ] APP 重启后状态正确。
- [ ] 备份包含挑战实例。
- [ ] 恢复后不会重复发奖。
- [ ] 模板更新不影响历史实例。
- [ ] 证据文件丢失时有明确提示。
- [ ] 月末结算正确。

### 交互体验

- [ ] 首页只有一个核心挑战入口。
- [ ] 当前阶段和下一步行动清楚。
- [ ] 不平铺所有里程碑和辅助信息。
- [ ] 关键操作有及时反馈。
- [ ] 低权限或无通知权限时仍可使用。

## 14. V1.0 未决事项

以下内容在正式开发前需要结合现有项目确认：

1. 当前数据库结构及模块边界。
2. 现有 XP 奖励曲线与挑战奖励具体数值。
3. 艺术收藏卡的最终视觉资源。
4. 每类挑战的实际内容配置和时间预算。
5. 推荐算法的权重。
6. 证据文件的存储上限。
7. 现有备份格式及迁移兼容性。
8. 当前首页与成长页面如何容纳挑战入口。

这些事项不应通过开发时随意猜测解决。

## 15. 最终交付定义

V1.0 不是一个展示挑战内容的页面，而是一套能够独立运行、记录、结算和恢复的成长系统。

正式验收必须证明：

- 用户可以收到合适的挑战。
- 用户能够自由决定是否接受。
- 接受后可以按规则完成。
- 进度和证据真实可靠。
- 奖励只发放一次。
- 完成成果可以长期保存。
- 不破坏向前现有的任务、XP、奖励账本及行为约束。

**只有完整闭环通过验收，月度挑战才算正式交付。**
